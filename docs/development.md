The public package is the repository root. Workspace packages are private implementation boundaries.

```bash

```

## Commands

```bash
bun run typecheck
bun run lint
bun test
bun run build
bun run verify:skills
bun run verify:docs
bun run verify:package
bun run sync:shared
bun run check
```

`verify:skills` checks frontmatter, invocation policy, UI metadata, size, placeholders, local
resource links, and shared-reference drift for all thirteen payloads. `verify:docs` checks public
Markdown structure, local links, changelog state, and package metadata.
`verify:package` inspects the exact file manifest produced by npm, the tool used for publishing.
`bun run check` runs it as part of the release-level local verification command.

## Architecture

- `agents.ts` owns agent definitions, discovery paths, and platform user-data paths.
- `skills.ts` is the single registry of packaged skills. A registry key is also the package,
  target, managed-store, and receipt ID.
- `scripts/shared-references.ts` maps each canonical file under `shared/` to the payload copies
  generated from it. A payload stays self-contained because a user can install one skill without the
  others, so shared normative text ships as a copy; the registry is what keeps the copies from
  drifting apart.
- `topology.ts` converts intended agents into the smallest native target set.
- `payload.ts` hashes, receipts, and atomically materializes one packaged skill.
- `installations.ts` inspects physical and linked installations.
- `operations.ts` implements install, update, removal, migration, and conflict policy hooks.
- `suite.ts` combines preflight results and provides rollback across a multi-skill confirmation.
- `transaction.ts` snapshots every touched path and performs compensating restore on failure.
- `ui.ts` implements the custom Clack Core rendering and diff viewer.
- `index.ts` owns interactive flows and user-facing policy.

Filesystem logic is UI-independent so tests can use isolated temporary homes and projects.

`run-feature` keeps orchestration state and completion guards in its bundled `orchestrator.ts`.
The host agent owns authenticated issue operations, native spawn/wait/cancel, and inspection of
checks, review and commit evidence. `host-worker.ts` prepares native packets or runs the Linux
Pi/Hermes supervisor; a transport exit is never stage completion.
Its watchdog records operation boundaries, input/error fingerprints, meaningful progress claims,
corrective instructions and recovery history. The host parent inspects these signals during bounded
waits. `worker-command.ts` preserves command evidence and `watchdog.ts` evaluates recurrence and
deadlines; the process supervisor honors recorded replacement only through owned-tree cleanup.
Native hosts use the same protocol with their actual message/wait/stop lifecycle. On Linux,
`worker-command.ts` and the process-host supervisor share `process-tree.ts` for dedicated subreaper
ownership and pidfd cleanup; native command receipts require terminal descendants. Other systems
need a verified native equivalent and are not covered by the Linux command execution fixtures.

`tests/feature-orchestrator.test.ts` covers recovery, identity, review continuation and completion
guards. `tests/feature-hosts.test.ts` uses explicit host/reviewer/forge doubles for packets and
process lifecycle, including a three-stage successful handoff; it makes no authenticated host claim.
`tests/feature-watchdog.test.ts` and command/host fixtures cover stalled operations, repeated errors
across fresh attempts, corrections, terminal replacement and explicit cancellation precedence.
`packages/cli/test/feature-skills.test.ts` exercises real payload install/update/remove in isolated
homes/projects across supported agents, scopes and copy/link strategies. `bun run check` also
checks shared references, invocation policy, UI metadata and the exact npm file manifest.
Observed Codex execution and the owner's documentary acceptance of the other four routes are
recorded in [compatibility](compatibility.md#feature-orchestration-acceptance). Changes to adapters
must still follow current primary sources and actual runtime preflight when executed.

`run-phase` uses an instruction-driven lifecycle and the canonical `shared/phase-workflow.md`, copied
into both phase skills. It delegates implementation to `run-subphase` and verifies actual Git,
slice/checklist and review evidence before advancement. It does not reuse the feature-only helpers
or ship a CLI process supervisor. The review-continuation block is generated for all three loops
from `shared/orchestration-review-continuation.md`; standalone bounded stops remain unchanged.
The orchestration payload matrix in `packages/cli/test/feature-skills.test.ts` also covers phase
install/update/removal while preserving the independent subphase executor.

## Adding a skill

1. Scaffold and validate the skill with the repository's supported skill-creation workflow.
2. Add a private workspace under `packages/<skill-id>` with `SKILL.md` and only the optional resource
   directories it needs.
3. Add the same stable ID and its display metadata to `SKILLS` in `skills.ts`; `SkillId` and
   `SKILL_IDS` are derived automatically.
4. Declare `policy.allow_implicit_invocation` in `agents/openai.yaml`. A skill that must not fire
   uninvited keeps that boundary at the instruction level: a minimal description ending with "Use
   only when invoked by name" plus an invocation section in the skill body. The hard
   `disable-model-invocation: true` flag remains supported but no current payload sets it, because
   hosts that honor it also refuse prompt-named invocation (see `docs/compatibility.md`);
   verification rejects the flag and the openai policy disagreeing. If the skill reuses text under `shared/`, register its copy in
   `scripts/shared-references.ts` and run `bun run sync:shared`.
5. Run skill and package verification. The package globs and verification scripts discover the
   registered payload automatically.
6. Test independent target/store paths, optional payload directories, suite rollback, update, and
   removal.
7. Update installation, target, update, removal, and release documentation.

## Adding an agent

1. Add its definition and documented paths to `agents.ts`.
2. Add its ID to `AGENT_IDS` and define project-scope support explicitly.
3. Update topology priority and shared discovery coverage.
4. Add isolated filesystem tests for user, project, copy, link, update, and partial removal.
5. Add the primary source and review date to `docs/compatibility.md`.
6. Update every public target table.

## UI principles

- Ask one decision at a time.
- Keep one blue accent plus semantic success, warning, and error colors.
- Show a preview before mutations.
- Keep destructive defaults conservative.
- Support `NO_COLOR`, keyboard-only use, cancellation, narrow terminals, and ASCII fallbacks.
- Use motion only as terminal feedback supplied by the prompt primitive, never as decoration.
- Keep every visible string concise and avoid decorative punctuation.
